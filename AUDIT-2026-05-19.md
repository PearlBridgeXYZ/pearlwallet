# PearlWallet v0.1.0 Security & Quality Audit
**Date:** 2026-05-19  
**Auditor:** Claude Code  
**Scope:** Complete TypeScript codebase, configuration, and crypto implementation  
**Status:** Ready for public GitHub release with noted issues below

---

## Executive Summary

**Overall Risk Assessment: LOW to MEDIUM**

PearlWallet is a well-architected non-custodial browser wallet with strong crypto foundations:
- All crypto operations correctly isolated in a Web Worker
- PBKDF2-SHA256 with 600k iterations + AES-256-GCM + proper WebCrypto-only implementation
- BIP-86 P2TR tweaking appears correct (tagged hash, point addition, x-only output)
- EIP-55 checksum correctly implemented
- No eval, dangerouslySetInnerHTML, or obvious XSS vectors
- CSP policy in nginx is strict and well-considered

However, there are **3 High-severity issues** and **1 Medium-severity issue** that should be resolved before public release:
1. **CRITICAL UX ISSUE**: Mock test hash generation using `Math.random()` leaking into codebase
2. **CSP Gap**: Relay API endpoints (`pearlbridge.xyz`) and Sentry not in CSP `connect-src`
3. **Missing Relayer Signature Verification**: EIP-712 mint signature not validated against on-chain RELAYER role
4. **Password strength UX**: Minimum 10 chars enforced but validation heuristic is basic

### 1. TEST HASH GENERATION LEAKS WEAK RNG INTO SEND FLOWS
**Severity:** CRITICAL  
**Files:** 
- `src/ui/pages/SendWPRL.tsx:58`
- `src/ui/pages/SendPRL.tsx:61`

**Issue:**
```typescript
// SendWPRL.tsx:58
```

- Shows up in history as a fake hash, but if the broadcast layer is incomplete, users might see "confirmed" false state

**Suggested Fix:**

```typescript
const hashBytes = new Uint8Array(32);
```

### 2. CSP MISSING RELAY API AND SENTRY ENDPOINTS
**Severity:** HIGH  
**File:** `/etc/nginx/sites-available/wallet.pearlwallet.xyz` (CSP header)

**Issue:**
Current CSP `connect-src`:
```
connect-src 'self' https://ethereum-rpc.publicnode.com https://eth.drpc.org
```

Missing allowed origins:
- `https://pearlbridge.xyz` (relay API for bridge intents & mint signatures)
- `https://pearl-sentry-fsn1-1.pearlbridge.xyz` (Pearl RPC sentry)
- `https://pearl-sentry-testnet.pearlbridge.xyz` (Pearl testnet RPC sentry)
- Possibly `https://pearl-sentry-fsn1-1.pearlbridge.xyz/` for Sentry error tracking (if enabled in future)

**Why It Matters:**
The wallet code makes `fetch()` calls to:
- `src/services/bridge.ts:79` → `${cfg.relayApiBase}/intents` (pearlbridge.xyz)
- `src/services/bridge.ts:91` → `${cfg.relayApiBase}/intents/{id}/mint-sig` (pearlbridge.xyz)

Once Pearl RPC sentry is fully provisioned (currently blocked as "TODO" in `src/services/balances.ts:36`), PRL balance reads will attempt:
- Pearl RPC JSON-RPC to `https://pearl-sentry-fsn1-1.pearlbridge.xyz/rpc`

CSP will **silently block these fetches**, causing the wallet to appear broken.

**Suggested Fix:**
Update nginx CSP to:
```nginx
add_header Content-Security-Policy "default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob:; font-src 'self' data:; connect-src 'self' https://ethereum-rpc.publicnode.com https://eth.drpc.org https://pearlbridge.xyz https://pearl-sentry-fsn1-1.pearlbridge.xyz https://pearl-sentry-testnet.pearlbridge.xyz; worker-src 'self' blob:; frame-ancestors 'none'; base-uri 'self'; form-action 'self'; object-src 'none'" always;
```

### 3. MISSING EIP-712 RELAYER SIGNATURE VERIFICATION
**Severity:** HIGH  
**File:** `src/services/bridge.ts:88–94`

**Issue:**
```typescript
export async function getMintSignature(network: EthNetwork, intentId: string): Promise<unknown> {
  const cfg = bridgeConfig(network);
  const res = await fetch(`${cfg.relayApiBase}/intents/${intentId}/mint-sig`);
  if (!res.ok) throw new Error(`relay /mint-sig: ${res.status}`);
  return res.json();
}
```

The function fetches a "signed mint payload" from the relay API but **never validates the signature against the on-chain RELAYER role**. The returned object is passed downstream without verification that:
1. The signer is actually authorized (holds the RELAYER role on BridgeController)
2. The EIP-712 signature is well-formed and over the correct domain/struct
3. The intent ID, amount, and recipient match what was submitted

**Why It Matters:**
A compromised or MITM-attacked relay could inject a signature for a different recipient, amount, or chain state. The wallet would broadcast it without catching the substitution. This is a **loss-of-funds vector**.

The relayer mint signature is critical to the bridge security model: users lock PRL on Pearl L1, the relayer observes and signs an EIP-712 intent to mint WPRL on Ethereum, and the user submits that signature to the bridge contract. If the signature is forged or for a different recipient, the user loses funds.

**Suggested Fix:**
1. Define the EIP-712 intent struct (domain, types, payload) per PearlBridge RC5 spec
2. After `getMintSignature()` returns, call `ethers.verifyTypedData()` or equivalent to recover the signer address
3. Fetch the BridgeController contract and verify the recovered signer has the RELAYER role:
   ```typescript
   const controller = getContract({ address: BRIDGE_ROUTER_ADDRESS[network], abi: [...], client });
   const hasRelayerRole = await controller.read.hasRole([RELAYER_ROLE_HASH, recoveredSigner]);
   if (!hasRelayerRole) throw new Error("E_SIGNATURE_NOT_FROM_RELAYER");
   ```
4. Also validate that the intent ID, recipient, amount, and network in the signature match the user's original submission

```typescript
export async function postSdiIntent(network: EthNetwork, sdi: unknown): Promise<{ id: string }> {
  const cfg = bridgeConfig(network);
  const res = await fetch(`${cfg.relayApiBase}/intents`, {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify(sdi),
  });
  if (!res.ok) throw new Error(`relay /intents: ${res.status}`);
  return (await res.json()) as { id: string };
}

export async function getMintSignature(network: EthNetwork, intentId: string): Promise<unknown> {
  const cfg = bridgeConfig(network);
  const res = await fetch(`${cfg.relayApiBase}/intents/${intentId}/mint-sig`);
  if (!res.ok) throw new Error(`relay /mint-sig: ${res.status}`);
  return res.json();

```

Both `fetch()` calls have no timeout. If `pearlbridge.xyz` or the relay is down or slow, the user will hang forever waiting for a response, with no visual feedback that a timeout occurred.

**Why It Matters:**
Poor UX: user sees "Bridge in progress" step 1 spinner indefinitely. No abort, no error message, no retry prompt.

**Suggested Fix:**
Add `AbortController` with timeout:
```typescript
export async function postSdiIntent(network: EthNetwork, sdi: unknown): Promise<{ id: string }> {
  const cfg = bridgeConfig(network);
  const controller = new AbortController();
  const timeout = setTimeout(() => controller.abort(), 15_000); // 15 second timeout
  try {
    const res = await fetch(`${cfg.relayApiBase}/intents`, {
      method: "POST",
      headers: { "Content-Type": "application/json" },
      body: JSON.stringify(sdi),
      signal: controller.signal,
    });
    if (!res.ok) throw new Error(`relay /intents: ${res.status}`);
    return (await res.json()) as { id: string };
  } finally {
    clearTimeout(timeout);
  }
}
```

## Medium-Severity Issues

### 1. WEAK PASSWORD STRENGTH HEURISTIC
**Severity:** MEDIUM  
**File:** `src/lib/validate.ts:23–32`

**Issue:**
```typescript
export function passwordStrength(password: string): PasswordStrength {
  const len = password.length;
  let score = 0;
  if (len >= 8) score++;
  if (len >= 12) score++;
  if (/[A-Z]/.test(password) && /[a-z]/.test(password)) score++;
  if (/\d/.test(password) && /[^A-Za-z0-9]/.test(password)) score++;
  const labels = ["too short", "weak", "ok", "strong", "very strong"];
  return { score: Math.min(score, 4) as PasswordStrength["score"], label: labels[Math.min(score, 4)]! };
}
```

The heuristic is basic: only length, case, and digit/special presence. A password like `Aaaaaaaaaa1!` (10 chars, case+digit+special) scores "very strong" even though it's highly compressible. Conversely, it doesn't account for:
- Common patterns (keyboard walks, repeated chars, dictionary words)
- Entropy from word length vs. character class combinations

Combined with a **minimum 10-character hard requirement** (enforced in `OnboardingCreate.tsx:65` and `OnboardingRestore.tsx:48`), users might think "10 chars = safe" and choose short passwords like `MyPass12!` (9 chars, rejected) or `MyPassword12!` (13 chars, accepted but low entropy).

**Why It Matters:**
Users with 10-char passwords might be overconfident in password security. The PBKDF2 mitigates this somewhat (600k iterations = ~0.5 second on modern hardware), but weak passwords are still weak.

The UI shows a strength label that users rely on. "Very strong" at 10 chars without special chars is misleading.

**Suggested Fix:**
Either:
- **Option A (recommended):** Use a proper strength library like `zxcvbn` (but adds bundle size):
  ```typescript
  import zxcvbn from "zxcvbn";
  export function passwordStrength(password: string): PasswordStrength {
    const result = zxcvbn(password);
    return { score: result.score, label: ["too short", "weak", "ok", "strong", "very strong"][result.score]! };
  }
  ```
- **Option B:** Tighten the heuristic to penalize low-entropy patterns:
  ```typescript
  let score = 0;
  if (len >= 12) score++;  // Raise minimum to 12
  if (len >= 16) score++;
  if (/[A-Z]/.test(password) && /[a-z]/.test(password)) score++;
  if (/\d/.test(password)) score++;
  if (/[^A-Za-z0-9]/.test(password)) score++;  // Special required, not paired with digit
  if (/(.)\1{2,}/.test(password)) score--;  // Penalize repetition
  ```
- **Option C (pragmatic):** Show a static message instead of a strength score:
  ```
  "Password must be at least 10 characters with uppercase, lowercase, a number, and a symbol."
  ```

**Severity:** LOW  
**File:** `src/ui/pages/Settings.tsx:144–163`

**Issue:**
```typescript
{showMnemonic && mnemonicValue && (
  <div className="card mt-3 bg-amber-50 dark:bg-amber-900/20">
    <p className="text-xs text-amber-700 dark:text-amber-400">

    </p>

    </pre>
    <button

        setMnemonicValue(null);

      }}
      className="btn-secondary mt-3"

    </button>
  </div>

```

When the user clicks "Hide", the mnemonic is cleared from React state. However, the string likely remains in the browser's DOM memory and JavaScript heap until garbage collection. A sufficiently determined attacker with process memory access (e.g., via malware) could extract it. Also, the password field `pwExport` is cleared, which is good.

**Why It Matters:**
Extremely low risk in practice because:
1. If an attacker has process memory access, the wallet is already compromised
2. The browser will eventually GC the string
3. The mnemonic is only displayed once, on demand, with a password gate

However, for maximum paranoia (warranted for a wallet), the mnemonic string should be wiped immediately after display.

**Suggested Fix:**
Use a `SecretString` or `Uint8Array` wrapper that explicitly wipes memory:
```typescript
// Utility function to securely display and wipe a string
function SecureStringDisplay({ text, onHide }: { text: string; onHide: () => void }) {
  useEffect(() => {
    return () => {
      // Wipe from memory on unmount (React will GC the component)
    };
  }, []);
  
  return (
    <div className="card mt-3 bg-amber-50 dark:bg-amber-900/20">
      <p className="text-xs text-amber-700 dark:text-amber-400">
        Don't screenshot this. Write it down.
      </p>
      <pre className="mt-2 whitespace-pre-wrap break-words font-mono text-sm">
        {text}
      </pre>
      <button
        onClick={() => {
          onHide();
        }}
        className="btn-secondary mt-3"
      >
        Hide
      </button>
    </div>
  );
}
```

Or simpler: replace the string with asterisks after N seconds:
```typescript
const [shouldShow, setShouldShow] = useState(true);
useEffect(() => {
  const timer = setTimeout(() => setShouldShow(false), 30_000); // Hide after 30 seconds
  return () => clearTimeout(timer);
}, []);

<pre>{shouldShow ? mnemonicValue : mnemonicValue?.replace(/\S/g, "*")}</pre>
```

### 10. BIP-86 TWEAK IMPLEMENTATION LOOKS CORRECT
**Severity:** INFO (CRYPTO REVIEW)  
**File:** `src/chains/pearl/address.ts:46–59`

```typescript
export function bip86Tweak(xOnlyInternal: Uint8Array): Uint8Array {
  if (xOnlyInternal.length !== 32) {
    throw new Error("internal pubkey must be 32 bytes (x-only)");
  }
  const tweak = taggedHash("TapTweak", xOnlyInternal);  // ✓ Correct tagged hash tag
  const internalPoint = secp256k1.ProjectivePoint.fromHex(
    Uint8Array.from([0x02, ...xOnlyInternal]),  // ✓ Prepend 0x02 for curve point recovery
  );
  const tweakScalar = bytesToBigInt(tweak);
  const G = secp256k1.ProjectivePoint.BASE;
  const tweakedPoint = internalPoint.add(G.multiply(tweakScalar));  // ✓ Point addition, not scalar addition
  const affine = tweakedPoint.toAffine();
  return bigIntToBytes(affine.x, 32);  // ✓ Return x-only (32 bytes)
}
```

Per BIP-86:
- `tweaked_output_key = internal_key + hash_TapTweak(internal_key) * G`
- The implementation correctly uses `tagged_hash("TapTweak", internal)` ✓
- Converts x-only internal to a point (adding 0x02 prefix for even-y recovery) ✓
- Multiplies G by the tweak scalar and adds (point addition) ✓
- Returns x-only output (32 bytes) ✓

The implementation is correct.

✓ **No action required.**

### 11. EIP-55 CHECKSUM IMPLEMENTATION CORRECT
**Severity:** INFO (CRYPTO REVIEW)  
**File:** `src/crypto/worker.ts:55–68`

```typescript
function toChecksumAddress(address: string): string {
  const addr = address.toLowerCase().replace(/^0x/, "");
  const hash = bytesToHex(keccak_256(new TextEncoder().encode(addr)));  // ✓ Keccak-256 of lowercase address
  let result = "0x";
  for (let i = 0; i < addr.length; i++) {
    const c = addr[i]!;
    if (parseInt(hash[i]!, 16) >= 8) {  // ✓ If hash hex digit >= 8, uppercase the address char
      result += c.toUpperCase();
    } else {
      result += c;
    }
  }
  return result;
}
```
