# Pearl Web Wallet v0.1.7 — Independent Adversarial Review (opus2)

**Scope:** v0.1.7 source tree at `.`, focus on the eleven question areas in the brief (concurrency, AAD migration, UTXO DoS, viem EIP-712, JSON boundary, KDF strength, build pipeline, storage, UI focus/paste, Worker isolation, partial-pool semantics).
**Method:** read-only; reviewed v0.1.6-opus2 only for format; did not echo prior findings.
**Verdict (one line):** v0.1.7 closes the headline H1/H2/H3 gaps from v0.1.6 cleanly. The remaining issues are real-but-bounded: (a) `worker-src 'self' blob:` in dist puts Vite's blob-worker URL on a CSP that is *missing* `frame-ancestors`, (b) production builds ship sourcemaps with `sourceMappingURL` annotations, (c) `makeAsyncLock` does NOT cover `init()`, the OTC-price-proxy fetch, or `useUI` mutations, (d) AAD is JSON.stringify — non-deterministic across engines if ever extended, (e) Worker `postMessage(WorkerCmd)` ships mnemonics/passwords by **structuredClone** — they linger in two heaps until GC.

---

## C — Critical

_None._ No primitive in v0.1.7 source maps to loss-of-funds today. Broadcast is still gated behind a disabled button (`SendPRL.tsx:174-183`), and `verifyRelayerMintSig.expected` is now type-required so the H1 regression vector is closed.

## H — High

### H1. Production build ships sourcemaps with active `sourceMappingURL` annotations → full reverse-engineering of Worker, including string literals and dev comments

`vite.config.ts:21` sets `sourcemap: true`. The build artifacts confirm it:
- `dist/assets/index-pLkVPW2o.js.map` (2.4 MB)
- `dist/assets/worker-_h1A9irR.js.map` (343 KB)
- `dist/assets/ccip-CZeput6n.js.map` (9 KB)

`grep sourceMappingURL` finds annotations in **all three** minified JS files (i.e., browsers auto-discover them in DevTools). Sourcemaps include unminified source plus comments like the AAD doc-string `"Pre-v0.1.7 AAD was a static \"pearl-web-wallet-v1\" label"` (keystore.ts:14) — handy reconnaissance for an attacker enumerating wallet versions and inferring which builds use which AAD.

Why High and not Info:
1. The dev comments cite past audit findings by number, structurally revealing the wallet's threat model and historical bug pattern to a targeted attacker.
2. The Worker map exposes the exact `pearlReceivePath(i)` derivation pattern, `RECEIVE_GAP_LIMIT = 20`, and the BIP-86 tweak helper — useful for an opportunistic attacker who has read a victim's `pearlAddressPool` but wants to derive past/future indices.
3. There is no operational reason to ship sourcemaps for a wallet that asks users to trust the static bundle ("your keys, your browser, your funds"). The standard wallet posture is `sourcemap: false` in prod and a separate uploaded-to-Sentry-style flow for crash analytics.

**Concrete cite:** `vite.config.ts:21` `sourcemap: true,` + `dist/assets/*.map` shipped.

**Fix:**
- Production: `sourcemap: false` (or `"hidden"` — emits files for upload but strips the `sourceMappingURL` annotation, so DevTools won't auto-discover).
- Ensure CF Pages doesn't serve `*.map`. Either delete them from `dist/` post-build or add a CF transform rule.
- Re-deploy.

Also note: `vite.config.ts` (TS) and `vite.config.js` (JS, lines 1-37) both exist and contain the same `sourcemap: true`. The JS one looks autogenerated; whichever Vite picks up first wins. The duplication is itself a footgun — fixing only `vite.config.ts` won't help if Vite is reading the `.js`.

### H2. `worker-src 'self' blob:` is present, but **frame-ancestors is missing from the <meta> CSP** — wallet can be iframed by any origin in non-CF deployments

`index.html:14-16` ships an http-equiv CSP that intentionally mirrors `public/_headers` "for non-Cloudflare deployments." Diffing the two:

| Directive            | `index.html` meta | `public/_headers` |
|----------------------|-------------------|-------------------|
| `frame-ancestors`    | **absent**        | `'none'`          |

The code comment at `index.html:8-11` acknowledges this: "frame-ancestors / HSTS / Permissions-Policy can't be set from a <meta> tag and stay on the response header." This is technically true (CSP3 §3.3.1 explicitly disallows `frame-ancestors` in meta) — but the **non-CF deployment** case (IPFS gateway, local static server, S3 mirror) the comment cites as the justification for the meta tag is **exactly** the case where the response header from `_headers` isn't applied. Result: the wallet on `ipfs://…` or any non-CF mirror can be embedded as an iframe and clickjacked through opacity tricks (the noindex hint at line 20 doesn't help — adversaries don't honour it).

Combined with the absence of `X-Frame-Options: DENY` in the meta path (also header-only), every non-Cloudflare mirror is iframe-able. A user who unlocks the wallet inside an iframe wrapped by `evil.example` sees the standard UI but the parent frame can paint a transparent overlay over the "Wipe" / "Show recovery phrase" buttons to harvest password clicks.

**Concrete cite:** `index.html:13-16` vs `public/_headers:2`.

**Fix:** Two options.
1. Document that IPFS/S3 deployments are unsupported, and gate `init()` on a runtime self-frame check: `if (window.top !== window.self) { document.body.innerHTML = "Pearl Wallet cannot run inside an iframe."; return; }`. Cheap, defense-in-depth, works without server-side headers.
2. Plus: emit a `<script>` at the top of `index.html` that does the self-frame check before React mounts.

Either is ~5 lines. I'd ship both.

### H3. `makeAsyncLock` does NOT serialize against `init()`, OTC-price fetch, `useUI` mutations, or **two** distinct BroadcastChannel allocations

`wallet-store.ts:109-127` defines the lock and threads it through `createWallet`, `restoreWallet`, `unlock`, `wipe`, `changePassword`, and the broadcast `onmessage` handler. What it does NOT cover:

**a) `init()` itself runs OUTSIDE the lock** (`wallet-store.ts:137-199`). React.StrictMode mounts the App twice in dev; in prod, a tab restoring from BFCache can hit `init` a second time. The `storeInitialized` flag is set *before* `await loadKeystore()` (line 142-143), which protects against duplicate channel allocation — but it does **not** serialize an `unlock` that races against init. Sequence:
1. Tab A is `status="initializing"`. User route-deeplinks to `/unlock` somehow (back/forward navigation, manual URL paste) and the form is renderable because `Unlock.tsx:1-60` doesn't gate on status.
2. User submits unlock → `walletLock(async () => { const { blob, pearlNetwork } = get(); if (!blob) throw E_NO_WALLET; ... })` runs.
3. If `init()` hasn't resolved yet, `blob === null` → unlock throws E_NO_WALLET even though there IS a keystore on disk.
4. User retries; init resolves between attempts; second unlock works.

Bounded UX bug — not a loss-of-funds — but it's the exact pattern that, in v0.2 with broadcast wired up, could produce a "create new wallet" path that resolves before `init()` had a chance to read the existing keystore. The `createWallet` guard at line 207-210 reads `loadKeystore()` so it catches that case today, but it's only one layer deep.

**b) Two BroadcastChannels in flight simultaneously.** `wallet-store.ts:85` (in `broadcastKeystoreEvent`) allocates a *new* BC each time it fires, distinct from the persistent BC at line 165. Both bind the same name `"pearl-wallet-keystore"`. BroadcastChannel does not loop messages back to the same channel object — but the persistent BC in Tab A receives a message from the ephemeral BC in Tab A's *own* `broadcastKeystoreEvent` call. So a Tab A `changePassword` fires `blob-updated`, which Tab A's *own* `onmessage` handler then processes, triggering `cryptoWorker.reset()` (line 181) — wiping the worker session we just got a new blob for. The user is force-locked the instant they change their password.

Actually — let me re-read. The standard BC semantics is "events fired on a channel will not be received by the same script context that fired them" (MDN), and a `new BroadcastChannel(name)` is a distinct script context. So the ephemeral BC in `broadcastKeystoreEvent` and the persistent BC in `init()` are **different** instances — meaning messages WILL be cross-delivered in the same tab. This is a real bug.

**Concrete cite:** `wallet-store.ts:82-91` (ephemeral BC) sends → `wallet-store.ts:166-194` (persistent BC) receives in the same tab. Run `changePassword`, the `blob-updated` handler will fire on the same tab, taking the new-password branch at line 180-183 → `cryptoWorker.reset()` + `set({status:"locked"})`. Net effect: a successful password change immediately locks the wallet.

**Fix:**
1. Reuse the persistent channel for fires: `keystoreChannel?.postMessage(ev)` instead of allocating a new one.
2. Or, tag every event with a session-unique sender id and have the handler ignore self-fired events: `const SENDER = crypto.randomUUID(); ... if (ev.data.sender === SENDER) return;`.
3. Wrap `init()` in `walletLock(...)` so concurrent initialization + mutation is serialized.

**c) `useUI` mutations (`ui-store.ts:50-66`) are NOT in the lock**, and `setPearlRpcOverride` is called from `Settings.tsx:162` while a balance refetch may be in flight reading `useUI.getState().pearlRpcOverride` via `pearl-rpc.ts:39-41`. Effect: a user changes RPC endpoint, the in-flight request fires against the *new* URL (since `rpcUrl()` is called per-request, line 54). Not a loss-of-funds — but it means a user pasting in a malicious RPC can immediately see balance data flow against it for any in-flight refetches. Minor.

### H4. Worker `postMessage(WorkerCmd)` ships `mnemonic` and `password` via **structuredClone** — copies sit in two heaps until GC

`worker-client.ts:33-40`:
```ts
call<C, R>(cmd: C, args: CmdArgs<C>): Promise<R> {
  ...
  w.postMessage({ id, cmd, ...args } as WorkerCmd);
}
```

Every `unlock`/`createWallet`/`restoreWallet`/`exportMnemonic`/`changePassword` ships `{password: string, mnemonic?: string}` as a *structured clone* — meaning the original string lives in the main thread's heap, AND a copy lives in the worker's heap, simultaneously, until JS GC eventually collects both. There is no way to zero a JS `string`; both copies persist as long as their respective contexts hold a reference.

Compounding: `worker.ts:212` and `worker.ts:231` retain the mnemonic on `session = { mnemonic, ...keys }` after deriving keys. The mnemonic string lives in the worker for the duration of the unlocked session. `wipeSession()` at `worker.ts:37-42` only zeroes the `Uint8Array` private keys; `session.mnemonic` is dropped by setting `session = null`, but the string itself is still pinned by V8 until GC. For a wallet auto-locking after 5 minutes, that's a sizable window where a heap dump (browser exploit, malicious extension with `chrome.debugger`, post-mortem crash dump auto-uploaded to a vendor) yields the mnemonic.

The "Web Worker isolates keys" design intent (`worker.ts:1-2`) is partially defeated by `WorkerCmd` carrying the mnemonic in plaintext at the boundary, and by keeping the mnemonic on `session` after derivation.

**Concrete cite:**
- `worker-client.ts:38`: `w.postMessage({ id, cmd, ...args })`
- `worker.ts:35`, `worker.ts:212`, `worker.ts:231`, `worker.ts:251`: `session = { mnemonic, ...keys }`
- `worker.ts:37-42`: `wipeSession` does not touch `session.mnemonic` because strings are immutable.

**Fix:**
- The mnemonic only needs to live in the worker long enough to derive the seed → master → child keys. After `seedFromMnemonic()` returns at `worker.ts:97-122`, the mnemonic can be dropped from `session`. The `exportMnemonic` and `changePassword` paths decrypt the blob fresh anyway (line 275, 283), so they don't depend on session-resident mnemonic.
- For passwords: structured-clone is hard to avoid for postMessage. But the wallet can mitigate by deriving a one-shot symmetric secret in the main thread, sending the *ciphertext* of the password to the worker, and decrypting inside. Overkill for v0.1.7; flag for v0.2.
- Audit the worker `session` type to drop `mnemonic: string` entirely. Re-derive keys at unlock time from the decrypted blob; don't keep the mnemonic resident.

## M — Medium

### M1. AAD is `JSON.stringify` of an object — order-stable in V8 today, but not specified

`keystore.ts:15-24`:
```ts
return new TextEncoder().encode(
  JSON.stringify({ v: version, kdf, iter: kdfIterations, c: cipher }),
);
```

V8 guarantees insertion order for non-integer keys, so today's output is stable. But:
1. ECMA-262 specifies enumeration order, not `JSON.stringify` key order specifically (the spec says `OwnPropertyKeys`, which V8 honors). A future engine (Bun, Hermes, an exotic embedded JS runtime someone might run the wallet in) MAY produce different orders. If it does, every previously-encrypted blob fails to decrypt on that runtime — `subtle.decrypt` with mismatched AAD throws, and `decryptBlob` catches and rethrows `E_PASSWORD_WRONG` (line 113-114). A user moving to a new engine sees "wrong password" for every attempt.
2. Adding a new AAD field in v2 is risk-prone. If `computeAAD` ever shifts to `{v, kdf, iter, c, hkdf}` and the AAD blob field is computed at encrypt-time but the live AAD constant updates, every v1-encrypted blob fails to decrypt.

The current code partially anticipates this — the blob stores `aad: Uint8Array` (line 37) and `decryptBlob` reads `blob.aad` rather than recomputing (line 107). Good. But there's no version-bump test: I see no `tests/keystore.test.ts` case that loads a fixture-encoded blob from an older version of the AAD format and asserts a graceful upgrade-or-reject.

**Concrete cite:** `keystore.ts:15-24` (non-canonical AAD construction), `keystore.ts:97-99` (rejects mismatched version but offers no migration).

**Fix:** Canonicalize. Either:
1. Concatenate fields with a fixed delimiter (`"v1|PBKDF2-SHA256|600000|AES-256-GCM"`) — order-deterministic by construction.
2. Or use a canonical JSON library (`canonicalize` package) — adds a dep.

Add a regression test that pins a hex-encoded v1 keystore blob and asserts `decryptBlob` produces the expected mnemonic. That guards both AAD drift AND any accidental KDF/cipher constant change.

### M2. `verifyRelayerMintSig` uses `recoverTypedDataAddress` — works, but no defense against a relayer signing for a DIFFERENT primaryType

`bridge.ts:173-179`:
```ts
const signer = await recoverTypedDataAddress({
  domain, types: MINT_TYPES, primaryType: "Mint", message: sig.payload, signature: sig.signature,
});
```

`primaryType` is hardcoded to `"Mint"` and `types` is hardcoded to the `Mint` struct. Good. But viem's `recoverTypedDataAddress` will happily accept a signature produced over a *different* struct collision — e.g., if the relayer signs a struct with the same field names but a different *types* definition (Mint as `{recipient, amount, sdiHash, nonce, deadline}` vs a hypothetical Withdraw with the same field names but different semantics), the recovered domain separator hash is identical because the type hash is computed from the field-name-and-type string concatenation, not from the struct name in isolation.

Actually — EIP-712's `typeHash = keccak256("Mint(address recipient,uint256 amount,bytes32 sdiHash,uint256 nonce,uint256 deadline)")` — the leading name **is** in the hash. So a relayer whose `BridgeController` Solidity source has a struct named "Withdraw" with the same fields would produce a *different* type hash, and `recoverTypedDataAddress` would recover a different signer. Wallet's check passes only if `BridgeController.hasRole(RELAYER_ROLE, signer)` — which a different-purpose attacker signer wouldn't have. So this is OK.

Still flag M because: the wallet doesn't verify `domain.verifyingContract` matches the in-flight `BridgeController` address against an on-chain check. `cfg.bridgeController` comes from `BRIDGE_ROUTER_ADDRESS[network]` (constant, baked at build time, RC5 address `0xA6571B73…`). If a v0.2 build mistakenly shipped with a stale or attacker-substituted address (compile-time supply-chain), the wallet would accept a signature signed against an attacker domain. Not a runtime exploit; a build-supply-chain canary.

**Fix:** Add a deploy-time CI check that runs against mainnet: `eth_call(BRIDGE_ROUTER_ADDRESS, "wprl()")` → must return `WPRL_ADDRESS`. Catches stale/substituted constants. The PearlBridge bundle canary memory note (`project_pearlbridge_bundle_canary.md`) addresses this for the **frontend** — extend it to cover the wallet bundle.

### M3. `coerceUint` in `normalizeRelayerMintSig` doesn't reject hex strings, scientific notation cleanly, leading "+"

`bridge.ts:97-109`. `BigInt("0x10")` returns `16n` — no error. `BigInt("1e3")` throws — good. `BigInt("+10")` returns `10n` — accepted. `BigInt(" 10")` (leading whitespace) returns `10n` — accepted. `BigInt("")` returns `0n` — caught at line 99.

The brief asks about `"0x..."`: a relayer that returns `amount: "0x10"` would parse as `16n`. If the relayer's intent was wire-format-decimal-string (per `bridge.ts:69`: "amount/nonce/deadline as JSON number or decimal string"), then a `"0x10"` from a malicious relayer is silently accepted and compared by `===` against `expected.amount` (a `bigint`). The mismatch check at `bridge.ts:167` will catch it because the user's `expected.amount` is computed from `parsePRL`/`parseWPRL` (decimal-only, see `format.ts:36`). So the bind catches the attack today.

But the failure mode "MITM relay returns hex-format amounts that happen to match" is technically possible. If `expected.amount = 1000000000000000000n` and the relay returns `amount: "0xDE0B6B3A7640000"`, both coerce to the same bigint, both compare equal — the binding check accepts. So hex-form acceptance doesn't break security here. Flag M for "polish/defense-in-depth": tighten `coerceUint` to require a decimal-only regex to match the relay wire-format contract documented in `bridge.ts:69`.

**Concrete cite:** `bridge.ts:97-109`.

**Fix:**
```ts
if (typeof field === "string" && !/^[0-9]+$/.test(field.trim())) {
  throw new Error("E_SIGNATURE_MALFORMED");
}
```
…before the `BigInt()` call. Forbids hex, scientific, signs, whitespace. Documents the contract.

### M4. `MAX_UTXO_WALK_PAGES = 20` + `PAGE = 100` is reasonable; per-page count is **not** capped

`pearl-rpc.ts:102` caps pages at 20. `pearl-rpc.ts:135` requests pages of 100. But the wallet does not enforce that the *response* contains ≤ 100 entries — the JSON-RPC sentry could return 100,000 transactions on page 1, and the for-loop at `pearl-rpc.ts:145-162` would happily iterate them.

Effect: A hostile sentry can ship a single page of 50,000 fabricated transactions referencing arbitrary `vin.txid:vin.vout` pairs. The walk is O(n) over vouts + vins, so it's bounded — but `seenOutputs` and `utxo` Maps grow to 50,000 entries each. With ~80 bytes/entry that's 4 MB per page, 80 MB across the 20-page cap. Tab might survive that, or might OOM on mobile. More importantly: the request body in `searchrawtransactions` response can be megabytes, and `await res.json()` blocks the JS event loop while it parses. The 250ms × attempt retry at `pearl-rpc.ts:51-52` plus the inter-address 300ms gap at `balances.ts:37` adds back-pressure, but a malicious RPC can still trivially keep a tab unresponsive for minutes.

**Concrete cite:** `pearl-rpc.ts:135-167`.

**Fix:**
```ts
if (!Array.isArray(page) || page.length > PAGE) {
  throw new Error("E_RPC_OVERSIZED_PAGE");
}
```
…right after the call. Caps memory and short-circuits the attack.

### M5. `partial` pool label semantics — *minor* HD-pool leak via timing, not via the label itself

The brief asks: does `prlSource: "partial"` leak which addresses failed?

`balances.ts:33-48` returns `{grains: bigint[], failures: number}`. The aggregated balance at line 74 is `result.grains.reduce(...)` and only the count `result.failures > 0` is surfaced as `partial`. Good — the UI doesn't render *which* index failed. Address indices stay private.

But the **serialized walk with 300ms gap** at `balances.ts:37` runs in deterministic order from index 0..N-1 (`worker.ts:101`). An attacker controlling the sentry can timing-attack: serve fast responses for indices 0-5, slow for 6-12, fast for 13-19, and time the wallet's overall response. The wallet doesn't randomize order or parallelize, so a network observer (or the sentry itself) learns which indices the wallet thinks it has, and roughly how long the wallet spent on each. Since `RECEIVE_GAP_LIMIT = 20` is constant and known, the sentry already sees all 20 indices being queried in order — there's no new privacy leak beyond the standard "RPC sees your addresses" model the Settings page already warns about (`Settings.tsx:296-299`).

**Verdict:** label is fine. Address-pool-via-RPC privacy was already weak by design.

### M6. `BroadcastChannel` is created in `init()` BEFORE `walletLock` wraps `init` — RACE under React.StrictMode

`wallet-store.ts:163-198`. In StrictMode, `useEffect(() => { void init() }, [])` runs twice. The `storeInitialized` flag (line 142) is checked synchronously and set before the `await loadKeystore()`, which IS atomic-enough — but the BC allocation at line 163-197 is AFTER `await loadKeystore()`. So the second StrictMode mount sees `storeInitialized=true`, returns early (line 142), and never runs the BC-allocation block. That's fine on first mount. But under HMR (Vite dev) the module reloads, `storeInitialized` resets to `false`, `init()` runs again, and a NEW BroadcastChannel is allocated while the OLD one (held in `keystoreChannel`) is still bound. The new allocation closes the old reference (line 100, only on `__resetWalletStoreForTests`), but `init`'s `if (!keystoreChannel)` guard at line 163 will skip the new allocation since the old reference is still set.

Net: in HMR you keep the stale BC. Production-only impact: zero. Dev-only annoyance.

**Concrete cite:** `wallet-store.ts:163`.

**Fix:** Move `keystoreChannel` reset into an HMR-aware hook, or stop fighting StrictMode/HMR and use a top-level `import.meta.hot?.dispose(() => keystoreChannel?.close())`. Low priority.

## L — Low

### L1. `passwordAcceptable` rejects mono-class but accepts `"aaaaaaaaaaA"` (11 chars, two classes, no entropy)

`validate.ts:44-61`. Floor passes mono-class but the 2-class check is satisfied by repeating one character of each class. `"aaaaaaaaaa1"` would pass length≥10 AND classes≥2. That's still ~30 bits of guessable entropy, far below the 600k PBKDF2 cost's break-even. Real users who pick this password get protected only by the PBKDF2 work factor, which a focused GPU/ASIC attacker burns through.

PBKDF2-SHA256 600k iterations is the floor for 2026 hardware. OWASP's 2026 cheat sheet recommends 600k for PBKDF2-SHA256 — so it's defensible. But Argon2id is the consensus modern choice (resists GPU/ASIC, tunable memory). For a wallet protecting mnemonic-at-rest, Argon2id with `m=64MB, t=3, p=1` is the standard. WebCrypto doesn't expose Argon2 natively — would need `@noble/hashes/argon2` (already a transitive via `@scure/bip39` likely) or a wasm shim. v0.2 work.

**Concrete cite:** `keystore.ts:4` `KDF_ITERATIONS = 600_000` (defensible), `validate.ts:52-58` (weak heuristic).

**Fix (M-level, but flagging here):** zxcvbn or similar real entropy estimator gated to ≥3 score for keystore passwords. The TODO at `validate.ts:22` ("zxcvbn deferred to keep bundle small") is owning the gap.

### L2. `Settings.tsx:108-113` `visibilitychange` handler hides mnemonic on `document.hidden` — but **does not clear `pwExport` if a timer is pending**

`hideMnemonic()` at line 54-60 clears `pwExport` too — good. But the `setInterval` callback at line 70-80 only clears `pwExport` when `s <= 1`. If the user hides the tab mid-countdown (say at second 30), `visibilitychange` calls `hideMnemonic()` which clears `pwExport` — fine. So actually OK. Cancel L2.

### L3. `Receive.tsx:60` `navigator.clipboard.readText()` may need user permission — silent failure means the auto-clear is unreliable

The 60-second clipboard-clear (line 58-67) wraps `readText` in try/catch. If the page lost focus (which is the *exact* case where you'd want the clear to fire), Chrome requires the page to be in focus to grant `readText` access. So the clear is best-effort, but the inline comment doesn't say that — line 64-65 just says "Permissions or focus restrictions — best-effort only." Users may assume the clipboard is wiped when it isn't. Minor UX/expectation issue.

**Fix:** Tighten the UI text near the copy button to reflect that clipboard auto-clear is best-effort. Or skip the `readText` check entirely and just `writeText("")` unconditionally — clobbering an unrelated paste-buffer-item is annoying but the only thing that guarantees the address is gone.

### L4. `prl-price.ts` (CF Pages Function) — proxy DOESN'T check `Origin` header

`functions/api/prl-price.ts:32-39` always sets `access-control-allow-origin: *`. Any site can fetch the proxy. The proxy itself doesn't expose anything sensitive (just an OTC price) — but `cf: { cacheTtl: 30 }` (line 89) means a popular abuse pattern (`*` CORS + free cached edge) makes this proxy a convenient amplifier for any frontend wanting free PRL prices. Not a wallet-security issue; an operational/cost concern.

**Fix:** Tighten ACAO to the wallet origin(s). Or accept it as a public price-API.

### L5. `Onboarding{Create,Restore}.tsx` use `autoComplete="off"` and `autoComplete="new-password"` — but **password manager interactions** are not isolated

Fine in practice. Bitwarden/1Password may still offer to autofill on mnemonic word fields (which use `type="password"` — `OnboardingRestore.tsx:97`). That's actually a useful flow if the user stored their mnemonic in their PM. Not a finding.

### L6. `ui-store.ts:30-46` uses `localStorage` — survives wipe

`wipeKeystore` at `db.ts:81-85` clears Dexie keystore + addressBook + txCache but NOT `localStorage`. After a wipe, the user's `pearlRpcOverride` (potentially pointing at a malicious sentry the attacker configured before they wiped) persists. If the attacker hands the device back to the victim and the victim restores from mnemonic on the same browser, the malicious RPC is still in effect.

**Concrete cite:** `db.ts:81-85` clears Dexie only.

**Fix:** Add `localStorage.removeItem("pearl-wallet-ui-v3")` to `wipeKeystore()`. Cheap.

### L7. `tip.ts:23-26` `TIP_ADDRESS_MAINNET` is a build-time constant

If an attacker substitutes the build (supply-chain), they can redirect tips. Not a primary attack vector — tip is opt-in and capped — but worth a deploy-time canary. Same fix family as M2.

### L8. Sourcemaps + dev comments referencing other private memory: low PII leak

Worker sourcemap exposes the inline comment at `worker.ts:7-9` referencing the oyster reference wallet (`pearl-research-labs/pearl`) by repo path. Not secret; already public. Info only.

## Info

### I1. `App.tsx:101-119` auto-route effect is missing from the dep array (eslint-disable comment, line 118)

`status` is the only dep listed and the disable is intentional. Standard React pattern; flagged Info only because future contributors will be tempted to "fix" the disable and add `location` → would route-loop on every nav.

### I2. `pearl-rpc.ts:81-88` `prlToGrains` uses `toFixed(8)` on a JSON-parsed float

A vout value of `0.10000001` from JSON parses as IEEE-754 ~`0.10000001000000000XYZ`. `.toFixed(8)` rounds to `"0.10000001"`. Good. But a vout value with more than 8 decimal places of significance (Pearl is 8-dp so this shouldn't happen on-chain, but a malicious sentry could send `0.123456789012`) gets silently truncated. Not exploitable — UTXO walk is over-counting safe because the rounding is consistent across credit and debit of the same vout (debit doesn't recompute; it just `utxo.delete(key)`).

### I3. `keystore.ts:40-45` `requireCrypto()` check happens at every call

Slight performance pessimization. Top-level check once would be fine. Not a security finding.

### I4. `RECEIVE_GAP_LIMIT = 20` is the BIP-44 standard but fixed

If a user restores from a wallet that uses index 21+, the wallet won't discover the balance. Documented at `hd.ts:18-22`. Info only.

### I5. `OnboardingCreate.tsx:84-86` uses `restoreWallet` instead of `createWallet` so the user-displayed mnemonic is preserved

The reason for this — the displayed mnemonic must match the persisted one — is documented inline (line 81-83). Good. Note: `restoreWallet` (`wallet-store.ts:242-277`) does no `validateMnemonic` check before passing through. The internal `seedFromMnemonic` does throw on bad mnemonics through `mnemonicToSeed`, but `worker.ts:228` explicitly validates in the `restoreWallet` branch — so this OnboardingCreate path is covered. Belt-and-braces.

### I6. `Settings.tsx:158-160` `parsed.protocol !== "https:"` check — but doesn't reject `https://attacker.local` or `https://192.168.1.1`

The CSP `connect-src` would block these at runtime (only `rpc.pearlwallet.xyz` and the two Eth providers are allowed). So defense-in-depth catches it. Info only.

### I7. No CSP `report-uri` / `report-to`

A CSP violation in a deployed wallet (e.g. a third-party script injection attempt) fires silently. For an opsec-conscious wallet I'd suggest a report endpoint. Out of scope; opinion only.
